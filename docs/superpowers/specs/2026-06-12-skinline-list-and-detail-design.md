# 皮肤套装列表优化与详情数据纠错设计

## 目标

优化 `/skinlines` 的套装浏览体验，使每个套装可正确进入详情页；同时从数据源修复套装详情皮肤错误，确保列表计数与详情皮肤集合一致。

## 已确认范围

- 保留 Header 现有全局搜索，套装列表不新增搜索功能。
- 列表支持按中文名称、皮肤数量进行升序或降序排序。
- 列表全量展示，不分页。
- 卡片使用项目 UI 框架的 `Item` 组件，仅展示中文名和皮肤数量。
- Item 使用响应式网格：桌面 3 列、平板 2 列、移动端 1 列。
- 整个 Item 可点击，进入稳定的套装详情路由。

## 前端设计

### 列表页面

`/skinlines` 保留当前 HomeTabs 导航结构，但将套装内容替换为独立列表组件。列表顶部只显示结果总数和排序控件，不放置局部搜索框。

排序状态通过 URL 查询参数表达，便于分享、服务端渲染和浏览器前进后退。默认按中文名称升序；名称相同时以 `riotSkinlineId` 作为稳定次级排序键，数量相同时先按中文名称再按 ID 排序。

每个 Item 使用 `skinlinePath` 生成 `/skinlines/{riotSkinlineId}-{slug}`，整个区域作为可访问链接。Item 只输出套装中文名和“共 N 款皮肤”。

### 详情页面

详情页只使用套装详情接口返回的结构化皮肤数组。移除通过列表接口和 `skinlineId` 皮肤分页接口拼装详情数据的第二套逻辑，避免多个事实源产生不一致。

## 后端数据设计

### 精确分组规则

皮肤的 `skinlineIdSets` 必须先拆分、去除空白并转换为完整整数 ID，再参与关联。禁止使用 `LIKE '%id%'` 或其他字符串子串匹配，因为套装 ID `1`、`17`、`19` 等会错误匹配 `171`、`170`、`193` 等值。

套装列表计数、详情皮肤查询和缓存构建必须复用同一个精确分组实现。

### 列表接口

套装列表响应在现有字段基础上增加：

```json
{
  "riotSkinlineId": 171,
  "name": "灵魂莲华",
  "skinCount": 35
}
```

前端只请求套装列表，不为统计数量加载全部皮肤。

### 详情接口

`GET /rest/lol/skinlines/{riotSkinlineId}` 返回套装基本信息、所属宇宙和使用完整 ID 精确匹配的皮肤数组。无关联皮肤时返回空数组，不返回其他套装数据。

## Redis 缓存

- 按套装 ID 保存皮肤分组或计数，缓存键遵循后端现有命名规范。
- 皮肤同步完成后，根据同步前后的套装 ID 集合主动重建受影响分组，覆盖新增、移除和套装变更。
- 缓存设置 TTL 作为兜底，不依赖 TTL 才更新正常业务数据。
- Redis 未命中时查询数据库、重建并回填缓存。
- 数据库查询失败时明确返回错误，不使用 `0` 或空数组伪装成功。
- 合法的空套装返回 `skinCount: 0`，详情返回空数组。

## 错误处理

- 套装不存在时详情接口返回明确的未找到响应，前端进入 404。
- 缓存不可用但数据库正常时允许从数据库读取，并记录缓存异常。
- 数据库不可用时请求失败，避免缓存缺失被误判为空数据。
- 前端收到缺失或非法 `skinCount` 时视为接口契约错误，不在客户端查询全部皮肤兜底。

## 测试与验证

### 后端

- 验证套装 ID `1` 不会匹配 `171`。
- 验证套装 ID `17`、`19` 等短 ID 只返回自身皮肤。
- 验证列表 `skinCount` 与详情皮肤数组长度一致。
- 验证 Redis 命中、未命中重建、TTL 和同步后的主动刷新。
- 验证套装从皮肤中移除后，旧分组计数同步减少。

### 前端

- 验证默认名称升序及名称降序。
- 验证皮肤数量升序及数量降序，并验证稳定次级排序。
- 验证 Item 使用正确的 `riotSkinlineId` 详情路径。
- 验证桌面、平板和移动端网格断点。

### 完成检查

- 执行受影响模块的定向测试。
- 执行 `npm run lint` 和 `npm run build`。
- 实际访问 `/skinlines`，检查排序、数量和跳转。
- 实际访问至少一个短 ID 套装详情，确认没有混入相似 ID 的皮肤。

## 非目标

- 不为套装列表新增局部搜索。
- 不新增分页或虚拟滚动。
- 不在前端加载全部皮肤计算数量。
- 不保留客户端精确过滤作为后端错误数据的长期兜底。
