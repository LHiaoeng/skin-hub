# 皮肤炫彩精确链接设计

## 目标

在不改变现有皮肤详情正式路由的前提下，让用户可以通过可复制、可刷新恢复的 URL 精确显示某个炫彩，并让页面内的炫彩切换状态与地址栏保持一致。

## URL 契约

- 原皮地址保持 `/skins/{skinId}-{slug}`。
- 指定炫彩使用 `/skins/{skinId}-{slug}?chroma={chromaId}`。
- `chromaId` 使用接口返回的 `SkinChroma.id`，只在当前皮肤的炫彩集合内有效。
- 切回原皮时移除 `chroma` 参数。
- 更新 `chroma` 时保留 URL 中其他查询参数。

## 数据流

1. 皮肤详情服务端页面继续通过路由中的 `skinId` 获取皮肤数据。
2. 页面合并结构化 `chromas` 与 `chromasJson`，并按炫彩 ID 去重，沿用当前 `buildVisuals` 的数据来源。
3. 服务端解析 `searchParams.chroma`，只接受可完整解析为有限正整数且能匹配当前皮肤炫彩的值。
4. 服务端将匹配到的 `chroma-{id}` 作为初始选中视觉传给 `SkinDetailViewer`；未匹配时传入原皮视觉。
5. 客户端所有现有切换入口继续调用统一的视觉选择函数。该函数在更新图片或视频状态的同时，使用 `router.replace` 同步查询参数。
6. 浏览器刷新或直接访问带参数地址时，服务端重新验证参数并恢复指定炫彩。

## 无效参数处理

- `chroma` 缺失时正常显示原皮。
- 空值、非数字、小数、非正整数、重复参数以及不属于当前皮肤的 ID 均视为无效。
- 无效参数不导致 404，也不使用相近 ID 或数组下标兜底；页面显示原皮，并在客户端挂载后通过替换当前历史记录移除无效 `chroma` 参数。
- 参数验证只使用当前皮肤的炫彩集合，避免链接误选其他皮肤的炫彩。

## 历史记录与交互

- 点击缩略图、点击底部色板和移动端上下滑切换均同步更新地址栏。
- 使用 `router.replace`，避免每次浏览炫彩都新增一条浏览器历史记录。
- URL 同步不触发跳转到新的详情页，现有背景保持原皮资源的规则不变。
- 选择没有视频资源的炫彩时，继续沿用当前自动回退静态图片的行为。

## SEO

- `chroma` 是同一皮肤详情页的展示状态，不创建独立可索引页面。
- canonical、Open Graph URL、JSON-LD 页面 URL 和站点地图继续使用不含查询参数的 `skinPath(skin)`。
- 页面 metadata 继续描述原皮，避免同一皮肤的炫彩参数产生重复内容。

## 验收标准

- 直接访问有效的 `?chroma={id}` 时，首屏选中并显示对应炫彩。
- 刷新页面后仍显示同一炫彩。
- 页面内切换炫彩后，地址栏使用对应 ID 且不新增浏览器历史记录。
- 切回原皮后，地址栏移除 `chroma`，其他查询参数保持不变。
- 无效或不属于当前皮肤的 ID 显示原皮并被移除，不返回 404。
- 原皮和带炫彩参数地址输出相同的原皮 canonical。
- 桌面端点击入口和移动端手势入口行为一致。

## 验证策略

- 为查询参数解析与视觉 ID 解析增加定向单元测试，覆盖有效、缺失、格式错误、重复和跨皮肤 ID。
- 执行 `npm run lint` 与 `npm run build`。
- 实际访问原皮、有效炫彩和无效炫彩 URL，验证首屏、刷新、地址栏同步、返回行为与 canonical。
